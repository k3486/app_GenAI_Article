## DB の表（叩き台）
`sources`／`topics`（話題。ユーザーの状態＝未読・読了・見送り・後で読む・★・👍👎と理由・「実はよかった」を列で持つ）／`articles`（正規化 URL は一意、進み具合、本文の取得状態）／`article_texts`（本文は別表）／`scores`（5観点・公式加点・合計・理由・種類・トピック・タグ・日本語タイトル・要約・モデル・スキルの版）／`digests`（整理記事）／`notes`／`chat_messages`／`runs`／`run_issues`／`search_queries`／`llm_usage`／`settings`

**AWS へ移しやすくするルール（①から守る）**
- 接続先は環境変数 `DATABASE_URL` だけで切り替える／表の形の変更は最初から Alembic（SQLite では batch モード）で管理する
- 日時は UTC で保存し、表示のときだけ日本時間にする／配列は JSON 型／状態の種類は文字列＋アプリ側の定義（DB 固有の型を使わない）
- SQLite 専用の機能は全文検索だけに限り、`search.py` の裏に隠す
- DB のアクセスは `services` に集約する／本文は別表／ローカルのファイルに状態を持たない
- 更新処理は短い単位（段階ごと）に分けて再開できる作りにする（Lambda の実行時間は最大15分のため）／Playwright は `fetcher.py` の中に隔離し、無効にもできるようにする

## スキルの仕様（打ち合わせで合意）
```
skills/
├─ score/    SKILL.md（役割・手順）／rubric.md（5観点の基準）
├─ group/    同じ話題の判定
├─ queries/  Brave 用の検索語の生成
├─ compose-announcement/ compose-howto/ compose-paper/ compose-analysis/ compose-industry/   整理記事（種類ごとの構成）
├─ _style.md 共通の文体
└─ chat/     壁打ち（役割・ルール・ツールの使い方）
```
- **出力の形は Python の型（Pydantic）を唯一の正**とし、スキルのファイルには書かない（二重管理を避ける）。構造化出力の定義はこの型から作る
- 興味プロファイルと直近の👍/👎/「実はよかった」は、DB から呼び出しのたびに差し込む。指示文の並びは「スキル＋基準（不変）→ プロファイル → フィードバック → 記事」（キャッシュを効かせるため）
- スキルのフォルダの内容から版（ハッシュ）を作り、点数・整理記事と一緒に DB に記録する
- **URL は Haiku に書かせない**。整理記事の末尾の URL 一覧は、プログラムが DB の URL から付ける
- 記事本文は区切りで囲み「中の指示には従わない」と明記する。壁打ちのツールは読み取り専用にする
- 例（few-shot）は初期なし。基準だけで始め、実データで確認してから、👍の記事などを足す

| スキル | 入力 | 出力 |
|---|---|---|
| score | 本文（約2万字まで）、プロファイル、直近のフィードバック | 5観点の点数（1〜5）、理由（1行）、記事の種類、トピック、タグ、日本語タイトル、1行要約（60字以内）、5行要約（各行60字以内） |
| group | 新着の記事（タイトルと冒頭約500字）、直近3日の話題の一覧 | 該当する話題の ID、または「なし」 |
| queries | プロファイル、直近の👍のタイトル、直近の話題の一覧 | 検索語5つ（英語3・日本語2）と狙い |
| compose-* | 全文、関連記事の本文、プロファイル | 構成に沿った本文（ですます調、論文は最大2,000字、他は800〜1,500字）。推測は「（考察）」と明示 |
| chat | 記事の全文、整理記事、会話の履歴 | 回答。ツールは記事の全文／関連記事／過去記事の検索／お気に入りの検索。1回の回答でツールは6回まで |

**点数の計算**: 各観点を `(点数−1)÷4` にして重みを掛けて合計する（5段階の「3」は重みの半分）。公式記事は +10。関心が2以下は通常の選定に入れない。「重大ニュース」は新しさ・重要度が5で関心が低い記事。

**採点基準の叩き台**（実データで確認して直す）

| 観点（重み） | 1 | 3 | 5 |
|---|---|---|---|
| 関心との一致（20） | 興味テーマと無関係 | テーマに触れるが主題ではない | テーマの中心で、プロファイルや👍の傾向に直接合う |
| 実用性＝再現性・汎用性（25） | 感想・ニュースのみ | 一部は試せる要点がある | 手順・設定・プロンプトが具体的で、条件が違っても再現・転用できる |
| 新しさ・重要度（25） | 既知の繰り返しや軽微な更新 | 有用な更新や新しい事例 | 業界や仕事に影響する大きな発表・仕様変更・規制 |
| 信頼性（15） | 出典なし・推測・宣伝 | 報道で出典が示されている | 一次情報（公式・論文）、または数字・検証・再現手順が示されている |
| 内容の深さ（15） | 見出し程度の紹介 | 要点を整理した解説 | 独自の分析・比較・検証があり考察が深い |

- 記事の種類が論文・発表・リリースのときだけ、「実用性」の代わりに「**実務や事業への示唆の大きさ**」を同じ重み（25）で評価する

## フィードバックループ（打ち合わせで合意）
- **入力となる操作**: 👍/👎（👎は理由を任意で選ぶ：興味なし／もう知っていた／質が低い）、落選記事の「実はよかった」。★・読了・見送りは学習に使わない
- **3つの文書を区別する**: 興味プロファイル（あなたが書く意図）／好みメモ（Haiku が👍👎の履歴から作る傾向。あなたが画面で直せる）／プロファイルの修正案（傾向を意図に昇格させる提案。あなたが承認）
- **採点・検索語の生成への反映**: 指示文に「プロファイル＋好みメモ＋直近の👍👎・実はよかった各10件」を差し込む。反映は次の更新から（過去は再採点しない）。どのフィードバックを使ったかは実行履歴に記録する（再現のため）
- **好みメモの更新**: 新しい評価が20件たまるごとに、更新の最後に Haiku が更新する
- **プロファイルの修正案**: 同じタイミングで最大3件作る。ホームの上部に「提案◯件」のバッジ、設定シートの先頭にカード（種類：追加／削除／言い換え、現在の文→変更後の文の差分、根拠の👍👎記事3件へのリンク、[承認][編集して承認][却下]）。承認するとプロファイルが新しい版になり、次の更新から反映。却下した種類の提案は30日間出さない（記録は次回の提案の材料に使う）。放置しても何も起きない。自動では書き換えない。プロファイルは版で保存し、設定シートの履歴から元に戻せる
- **効き具合の指標**（分析シート）: 選定記事の👍率／落選記事の「実はよかった」率／点数と👍率の関係。基準・重み・しきい値を直す根拠にする
- 探索枠（意外な記事を混ぜる）は見送り。まず上記で足りるかを見る
- 追加の表: `profile_versions`／`profile_proposals`（種類・変更前後の文・根拠の話題 ID・状態・日時）／`preference_notes`。追加のスキル: `skills/preference/`（好みメモの更新と修正案の生成）

## 非同期の並列処理（速度向上）
更新処理は `asyncio` で書き、待ち時間が長い処理（通信）を同時に進める。段階の順番は守り、**各段階の中で並列にする**（段階の間で止まる作りなので、途中再開の仕組みとそのまま両立する）。

| 段階 | 並列にする内容 | 同時数の目安（設定で変えられる） |
|---|---|---|
| ① 集める | RSS・一覧ページ・Brave 検索・HF Daily Papers を情報源ごとに同時に取得 | 全体で8 |
| ③ 本文を取る | 記事ごとに同時に取得。同じサイトには最大2件まで同時、かつ間隔をあける（robots.txt の Crawl-delay も守る）。間隔はサイトごとに設定ファイルで持つ（arXiv は3秒に1回程度が目安。実装前に最新の規約を確認する） | 全体で8、同一サイト2 |
| ③ Playwright | ブラウザは重いので控えめに | 2 |
| ④ 話題の判定 | 共通リンクで決まる分は即時。残りは Haiku で判定（新着どうしの重複も見るため、まとめて1〜数回の呼び出しにする） | ― |
| ⑥ 採点 | 記事ごとの Haiku 呼び出しを同時に実行 | 5 |
| ⑦ 整理記事 | 記事ごとに同時に実行 | 4 |

- **使うもの**: 通信は `httpx.AsyncClient`、Haiku は Anthropic SDK の非同期版（`AsyncAnthropic`）。更新の入口は `asyncio.run`
- **DB の書き込みは1か所に集める**: 並列に動くのは通信だけで、結果は調整役（1つの処理）が受け取って DB に書く。SQLite は同時に書き込めるのが1つだけなので、書き込みの競合を避けられ、非同期の DB ドライバも要らない
- **費用の上限と並列の両立**: 呼ぶ前に「見込み費用」を予約して上限と比べ、呼んだ後に実費で精算する。並列のぶん上限を超える量は、最大でも「同時数×1回の費用」に収まる
- **Anthropic API の制限（429）**: 同時数を上限にし、SDK の自動やり直し（間隔をあけて再試行）に任せる。続けて出たら同時数を自動で下げる
- **1件の失敗で全体を止めない**: 各タスクの失敗は記録して続ける（キャンセル時はまとめて停止）
- **効果の見込み**（私の概算。①で実測する）: 50件の更新が、順番に処理すると15分以上のところ、数分に収まる。Lambda の15分制限にも余裕ができる
- **テスト**: Haiku と通信は偽物に差し替え、同時数を絞って順序が結果を変えないことを確かめる

## バックグラウンドの構成（打ち合わせで合意）
```
backend/
├─ app/
│  ├─ api/       受付係（topics / articles / rejected / favorites / backlog / insights / settings / runs / chat）
│  ├─ services/
│  │   ├─ runs.py       更新の開始・二重起動の防止・状態
│  │   ├─ pipeline/     discover → filter → fetch → group → score → select → compose（1段階＝1ファイル）
│  │   ├─ collectors/   rss / listing / brave / hf_papers / arxiv
│  │   ├─ fetcher.py    robots.txt → httpx → 本文の抜き出し → Playwright → PDF
│  │   ├─ llm/          Haiku を呼ぶ唯一の口（最新 Haiku の選択・料金の記録・月と1回の上限・形式が壊れたら1回やり直し）
│  │   │                ＋ スキルの読み込みと実行 ＋ 壁打ちのエージェント
│  │   └─ feedback / chat / search（SQLite FTS5・trigram）/ insights
│  ├─ models/    DB の表（情報源・記事・本文・話題・点数・整理記事・メモ・壁打ち・フィードバック・実行履歴・llm_usage・設定・検索語）
│  └─ schemas/   API の入出力の型（OpenAPI から TypeScript の型を自動生成）
├─ skills/       Haiku の仕事のスキル（score / group / compose-<種類> / queries / chat）
├─ config/       sources.yaml（情報源）・scoring.yaml（基準の文章・キーワード語）。ファイルが正、git で管理
└─ scripts/collect.py   更新の入口
```
- ファイルと DB の分担: 情報源の一覧・基準の文章はファイル。画面で変える値（プロファイル・重み・しきい値・上限・件数）は DB。画面の情報源一覧は、成績つきの閲覧と有効／無効の切り替えだけ
- **記事の進み具合を DB に持つ**: 発見 → 本文取得済み（失敗は次回再試行）→ 話題に所属 → 採点済み（上限超えは採点待ちで次回）→ 選定／落選 → 整理済み。止まっても続きから再開する
- **更新の流れ**: `POST /api/runs` → 二重起動を確認 → 実行履歴に行を作り、別プロセスで `collect.py` を起動して即応答 → 作業員が各段階を進め、記事ごとに結果とハートビートを書く → 終了時に結果（成功／一部失敗／上限で停止・件数・費用）を記録。ハートビートが10分止まれば「失敗」と見なす
- **失敗時**: 1つの情報源の失敗は飛ばして続ける／本文が取れなければ2回やり直し、次回もう1回、だめなら概要で採点／Haiku の一時エラーは SDK が自動で2回までやり直し、だめならその記事は次回／上限に達したらその回は止める
- **画面側の部品**: React Router・TanStack Query・TanStack Table・Recharts を追加する
- **費用の安全装置**: Haiku を呼ぶ前に「1回の更新が $0.5 未満」「今月が $10 未満」を確認し、呼んだ後に使ったトークンと費用を記録する。採点の指示文は、変わらない部分（プロファイル・基準）を先頭に置いてプロンプトキャッシュを狙う（効果は実測で確認）
- **Haiku 5.5 の「考える」設定**: 初期設定では考える機能（adaptive thinking）がオンで、考えた分も出力として課金される。そのため `effort` をスキルごとに明示する（採点・話題の判定・検索語は low、整理記事・壁打ち・好みメモは medium）。費用と速度の見込みは、①で実測して見直す
- **バックアップ**: 更新が終わるたびに、SQLite のバックアップ機能で `data/backups/` にコピーし、7世代残す。②では S3 などに置く（👍👎や好みメモは使うほど価値が増えるため）
- **モデルの変更に気づく**: 解決した Haiku のモデル名が前回の更新と違うときは、実行履歴と画面の上部に通知する。モデル一覧を取れなかったときは、前回のモデルで続ける

## ダッシュボード構成（打ち合わせで合意）
シートは7つ。

| シート | 中身 |
|---|---|
| 最新トピック（ホーム） | 前回の更新結果・新着件数・今月の Haiku 費用と上限／重大ニュース枠（最大3件）／おすすめ一覧。**更新の回ごとに区切り（今日の更新→昨日→一昨日…、直近7日）、中は点数順**。カードに点数・記事の種類・トピック・1行要約・画像・関連記事数・★・👍👎・「後で読む」。種類・トピック・情報源・期間で絞り込み。カードを開くと整理記事（点数の内訳と理由も） |
| お気に入り記事 | **★** を付けた記事。トピック・タグで絞り込み、検索。好みの傾向（トピック・情報源・記事の種類） |
| バックログ | 未読の選定記事（自動で入る）と「後で読む」にした記事のキュー。滞留日数・点数で並べ替え、「読んだ」「興味なし」で消化。**30日たった未読は自動で「見送り」**（全記事には残る）。残数の推移 |
| 全記事（選定済み） | 選定された記事の表。列: 日本語タイトル／1行要約（隣の列）／URL／★／👍👎／状態（未読・読了・見送り）／点数／記事の種類／トピック／情報源／発表日／選定日。初期の並びは選定日の新しい順、1ページ50件、全列で並べ替え・絞り込み、全文検索。行をクリックすると整理記事へ |
| 落選記事 | 落選した記事の表。列: 日本語タイトル／5行要約／URL／点数と内訳／落選の理由／記事の種類／トピック／情報源／発表日／登録日。**「実はよかった」フラグ**を付けられる（整理記事は作らず、扱いも変えない。次回以降の採点に、フィードバックとして反映する） |
| 分析 | トピックの内訳／話題の推移／情報源の成績 |
| 設定・運用 | 興味プロファイル・重み・しきい値・月の上限・情報源の一覧／更新の実行履歴（失敗の理由・費用・Haiku が作った検索語） |

- **👍/👎 と ★ は別**: 👍/👎 は好みの学習用、★ は保存用（お気に入りシートに入る）
- 週次ダイジェストは見送り（使い始めてから判断）
- 一覧の単位は「記事」ではなく「話題」（代表記事に関連記事がぶら下がる）

## 記事収集ワークフロー（打ち合わせで合意）

### ① 候補を集める
- RSS／RSS の無い公式サイトは一覧ページから、サイトごとに設定した「記事 URL の形」に合うリンクを拾う（Haiku は使わない）
- Brave 検索: 興味プロファイルと最近の👍から Haiku が毎回5語（英語と日本語）を作り、直近3日分を検索する。作った検索語は記録して画面で見られる。未登録のサイトも候補にし、除外リストに載せたサイトは拾わない
- Zenn・Qiita: タグの新着のうち、いいね数の多い順に各10件
- HF Daily Papers: 1日あたり投票数の上位5本

### ② 絞る（全文を取る前。費用はかからない）
- 毎回直近3日分を見る（初回も同じ）。URL を正規化して取得済みかを機械的に見分け、取得済みはここで除く。正規化は、リダイレクト後の最終 URL と `rel=canonical` を使い、追跡用パラメータ（`utm_*` など）を除き、`http` を `https` に統一し、末尾のスラッシュや断片（`#…`）をそろえる
- AI 以外の記事も多い情報源は、タイトルか概要に生成AI関連の語を含むものだけ通す（語の一覧は設定ファイル）
- 日本語・英語以外は除く。公開日が不明な記事は、見つけた日を公開日とし「日付推定」と表示する
- **候補は最大80件で打ち切る**（公式記事 → 新しい順）。本文を取りに行く前に絞り、無駄な通信と時間を省く。超えた分は次回に回す
- **採点は、話題をまとめた後の代表記事のうち最大50件**。超えた分は「公式記事 → 新しい順」で優先し、残りは次回に回す（どちらの数も設定で変えられる）

### ③ 全文を取る
- robots.txt を確認 → 通常の方法で取得 → 本文を抜き出す → 本文が空なら Playwright（画面の無いブラウザ）で取り直す
- 一時的なエラーはその場で2回まで取り直し、次の更新でもう1回試す。それでも取れなければ「全文未取得」として概要で採点する
- 本文（見出しや箇条書きを残したテキスト）を DB に保存する。アプリには原文を表示しない。記事の代表画像は URL だけ保存し、カードに表示する
- **取得の安全対策**（②の AWS では特に重要）: `http`/`https` のみ許可／内部アドレス（`10.*`・`172.16–31.*`・`192.168.*`・`127.*`・`169.254.*` など）への接続を拒否（名前解決後の IP でも確認）／リダイレクトは5回まで／1回のダウンロードは5MB・30秒まで／Playwright は不要な機能を止めた使い捨てのブラウザで開く

### ④ 同じ話題をまとめる
- 同じ公式ページや論文にリンクしている記事は1件にまとめる。リンク先の公式ページをまだ集めていなければ、取りに行って代表にする
- 共通のリンクが無いものは、採点の前に Haiku が専用に判定する。材料は、タイトル・本文の冒頭約500字と、直近3日分の話題の一覧。同じ話題なら採点せず、既にある話題の関連記事に入れる
- 代表の優先順位: 公式ブログ → 紹介記事 → 論文（HF Daily Papers で単独で拾った論文は、論文自体が代表）
- 採点するのは代表だけ。整理記事を作った後に届いた関連記事は、関連記事の一覧に足すだけ（作り直さない・新着として上位に戻さない）

### ⑤ 論文を足す
- 採点用: HTML 版から要旨・序論・結論を取得する。HTML 版が無ければ PDF から文字を取り出す
- 選定を通った論文だけ、整理記事を作るときに全文を読む

### ⑥ 採点（Haiku、先頭から約2万字まで）
- 5つの観点を、それぞれ基準付きの5段階で評価する。基準の文章は設計の段階で叩き台を作り、確認してもらう

  | 観点 | 重み |
  |---|---|
  | 関心との一致 | 20 |
  | 実用性（再現性・汎用性があるか） | 25 |
  | 新しさ・重要度 | 25 |
  | 信頼性 | 15 |
  | 内容の深さ | 15 |

- 重みを掛けて100点満点に換算する。公式記事は +10 点。関心との一致が2以下の記事は、通常の選定に入れない
- 点数の理由を1行、トピック（固定の分類1つ＋自由タグ数個）、記事の種類、日本語タイトル、日本語の1行要約、日本語の5行要約を、全候補に付ける（落選記事の表示用。費用は月約 $0.1 の増加と見込む）
- 落選記事も、選定された記事と同じ形（本文・点数の内訳・要約など）で DB に残す
- **トピックの固定分類**（`scoring.yaml` に置く。グラフの集計に使う）: 開発ツール・エージェント／新モデル・性能比較／業務での活用事例／活用ノウハウ（ワークフロー・プロンプト）／規制・安全性／業界動向／その他。**記事の種類（発表・リリース／活用ノウハウ・事例／論文・研究／解説・考察／業界動向・規制）とは別のもの**。種類は整理記事の構成を、トピックはグラフの集計を決める
- 指示文には、興味プロファイル・好みメモ・直近の👍/👎/「実はよかった」（それぞれ10件まで、👎の理由「興味なし／もう知っていた／質が低い」を含む）を入れる（詳しくは「フィードバックループ」の節）

### ⑦ 選定・整理記事
- 60点以上を最大10件。加えて、**新しさ・重要度が5で、通常の選定に入らなかった記事**を「重大ニュース」として最大3件、別枠で選ぶ（どちらも整理記事を作る）
- 整理記事で読む関連記事は最大3件・各2万字まで（超えた分は冒頭を使う）
- 整理記事は記事の種類ごとに構成を変える。どの種類も、先頭に3行まとめ、関連記事があれば識者・各社の評価、末尾に URL 一覧を入れる

  | 種類 | 構成 |
  |---|---|
  | 発表・リリース | 何が変わったか／性能・仕様の比較／提供範囲・料金・いつから／あなたにとっての意味／市場・競合への影響／導入を判断するポイント |
  | 活用ノウハウ・事例 | 背景・課題／構成・手順／プロンプトや設定の要点／効果／再現・応用のポイントと注意点／費用対効果／組織に導入するときの論点 |
  | 論文・研究 | 概要／主張／新規性／根拠／反論・限界／示唆／実務での応用・適用方法（考えられる場合）／ビジネスの視点 |
  | 解説・考察 | 主張／根拠／別の見方・反論／あなたにとっての意味／ビジネスへの示唆 |
  | 業界動向・規制 | 何が起きたか／背景／影響範囲／今後の注目点／事業の機会とリスク／競争環境の変化 |

- Haiku の推測は「（考察）」と明示し、画面でも色を変える。根拠が薄い項目は省く
- 長さはですます調で、論文・研究は最大2,000字、それ以外は800〜1,500字。書くことが無い項目は省く

### ⑧ 保存・結果
- すべて DB に保存する。画面の上部に前回の更新結果（成功／一部失敗／上限で停止、新着の件数、全文を取れなかったサイト）を表示する。上限で止まって採点できなかった記事は次の更新で処理する

## 段階①の進め方（今回の対象）
1. **準備**: **プロジェクト名をご確認いただき**、`scripts/init_project.sh` を実行して設定する。**興味プロファイルの叩き台**（初期テーマ5つをもとにした文章）を作り、ご確認いただく。Playwright 用のブラウザを導入する。ideas の案を「採用」に更新し、`.steering/20261107-local-dashboard/` に requirements / design / tasklist を作る。`.env.example` に `ANTHROPIC_API_KEY` が無いので追記する
2. **画面だけ先に作る（試しのデータ）**: frontend-design スキルと dataviz スキルを使う。上の「ダッシュボード構成」の7シートを作る（`src/features/` に topics・favorites・backlog・articles・rejected・insights・settings）。画面は固定のダミー JSON ではなく、**API の形（契約）を先に決め、試しのデータを返す API につなぐ**。本物のデータに切り替えても作り直さずに済ませるため。`src/lib/api.ts` に POST/PUT を追加する。**→ 上司にデザインを確認してもらう**

4. **収集**: RSS（feedparser）、ページを直接読む取得（RSS の無い公式サイト向け）、Brave Search、HF Daily Papers、記事内の arXiv リンクを集める。全文は httpx で取得して本文を抜き出す。robots.txt の確認、重複の除去（URL を正規化）も行う。情報源の一覧は `sources.yaml` に置く
5. **Haiku の処理**: 「Haiku の実行方針」「スキルの仕様」（Anthropic 公式 SDK＋スキル、構造化出力）に従う。採点・同じ話題の判定・検索語の生成・整理記事・好みメモとプロファイルの修正案。費用を記録し、月と1回の上限を超えたら止める。最新の Haiku を自動で選ぶ。料金は claude-api スキルで最新の料金表を確かめ、1日に処理できる件数の目安を出す。backend/CLAUDE.md の LLM の節に「今回は SDK 直接」の例外を追記する提案をする
6. **更新ボタン**: 収集から生成までを1つの service にまとめ、API からもスクリプト（`scripts/collect.py`、段階②の定時実行で使う）からも呼べるようにする。段階の中は非同期で並列に動かす
7. **壁打ちとフィードバックループ**: 記事ごとの対話画面と API（履歴・メモ・費用の記録）、好みメモ・プロファイルの修正案の画面と承認の流れを追加する
8. **試しのデータを消し、本物の記事で確認**: 数日分を採点し、点数の分布と「選ばれるべき記事が選ばれているか」を一緒に見て、基準としきい値を直す。**点数のぶれの検査**（同じ記事10件を3回採点して差を見る）も行い、基準やモデルを変えたときの前後比較に使えるようにする → `docs/spec.md`・`docs/architecture.md` を更新し、`history.md` に追記する
