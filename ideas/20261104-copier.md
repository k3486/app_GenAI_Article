# Copier（copier.yml）の導入

状態: 不採用（理由: テンプレートから作ったアプリが0件で反映先がない。2〜3件になったら再検討）

## 背景
今は GitHub の「Use this template」＋ `scripts/init_project.sh`（名前の置換・記録のリセット）で新しいアプリを作る。
この方式では、作った後にテンプレートを改善しても、既存のアプリには反映できない（手で写すしかない）。

## 案
Copier を使い、テンプレートに `copier.yml`（質問と変数の定義）を置く。
- 作成: `uvx copier copy gh:k3486/app-template <新しいフォルダ>` → 名前などを聞かれて生成
- 更新: アプリ側で `copier update` → テンプレートの新しい版の差分を取り込む（衝突したら手で解決）
  - 条件: アプリに `.copier-answers.yml` があること、テンプレートが git のタグで版管理されていること、アプリ側が git 管理で変更なしの状態
  - 出典: copier docs「Updating a project」（context7: /copier-org/copier）

## 比較
| | 今の方式 | Copier |
|---|---|---|
| 新規作成 | GitHub のボタン＋スクリプト1本 | コマンド1本（質問に答える） |
| テンプレート改善の反映 | できない（手作業） | `copier update` で取り込める |
| テンプレート自体の動作確認 | そのまま `make lint/test` できる | 名前を差し込むファイル（package.json 等）を `.jinja` にすると、テンプレートのままでは動かない |
| 維持の手間 | 少ない | タグ付け（版管理）・Jinja の記法・更新時の衝突解決が増える |

## 判断の目安
- 今はテンプレートから作ったアプリが 0 件で、反映先がない → 今は導入しない
- アプリが 2〜3 件になり、テンプレートの改善を手で写す手間が実際に出てきたら再検討する
- CLAUDE.md の共通ルールは既に `~/.claude/CLAUDE.md` に分けたので、改善の多くはテンプレートを経由せず全アプリに効く
